## What CSXCAD is, and is not

CSXCAD is a standalone LGPLv3 C++ library for describing geometry and the
physical properties attached to it, serialized as XML. openEMS is its largest
user, but CSXCAD does not depend on openEMS and is versioned, released and
documented independently. Anything that only makes sense inside an FDTD solver
belongs in openEMS, not here — CSXCAD stores and serializes values, it does not
interpret them.

## Architecture in 60 seconds

- **`ContinuousStructure`** (`src/ContinuousStructure.h`) is the root container:
  a `ParameterSet` of named symbolic parameters, a `CSRectGrid` (rectilinear
  mesh), a `CSBackgroundMaterial`, and a list of `CSProperties*`.
- **`CSProperties`** (`src/CSProperties.h`) is the abstract base for every
  material/excitation layer (`CSPropMaterial` and its dispersive subclasses,
  `CSPropMetal`, `CSPropExcitation`, `CSPropProbeBox` → `CSPropDumpBox`, …).
  Each property owns a list of primitives.
- **`CSPrimitives`** (`src/CSPrimitives.h`) is the abstract base for geometry
  (box, sphere, cylinder, polygon, polyhedron, curve, point, …). Any primitive
  can carry a **`CSTransform`** (`src/CSTransform.h`).
- **`ParameterScalar`** holds either a literal double or a named-parameter
  expression evaluated through fparser; `ReadTerm`/`WriteTerm` in
  `src/ParameterObjects.h` handle its XML form.

Two consequences worth internalising:

- **The XML is a public file format.** Element and attribute names are API.
  Existing files must keep loading — add new optional attributes, never rename
  or repurpose an existing one.
- **A user-visible feature usually needs three interfaces.** The C++ class, the
  Cython binding in `python/CSXCAD/` (`.pxd` declarations and `.pyx`
  implementation — the `.cpp` next to them is generated by Cython at build time
  and gitignored, so never edit it), and the pure M-file interface in
  `matlab/`, which writes the same XML.

## Python binding semantics

Rules the bindings rely on — break one and the failure is a use-after-free or a
silently duplicated object, not a compile error:

- **Ownership transfers to C++.** `AddProperty`, `AddPrimitive` and
  `SetTransform` hand the object over; the Python wrapper is a borrowing handle
  afterwards. Use `.copy()` (on `CSTransform`) first if you need to keep an
  independent object.
- **One wrapper per C++ object.** `CSTransform.fromPtr` keys a class-level
  `_instances` dict on the pointer, so `SetTransform(t); GetTransform() is t`
  holds. Preserve that identity when adding a `fromPtr`-style constructor.
- **Objects you can only obtain from a parent** (e.g. `CSBackgroundMaterial`)
  raise `TypeError` on direct construction.
- **`no_init=True`** allocates a Python shell without creating a C++ object;
  `fromPtr`/`fromType` use it to wrap existing pointers.

## Gotchas

- **TinyXML1 `SetAttribute` truncates doubles** — use `SetDoubleAttribute()` for
  every floating-point XML attribute, or values silently lose precision on
  write.
- **`hid_t` is 64-bit** on modern HDF5. Never store one in an `int`; the
  truncation breaks every subsequent type comparison without a warning.
- **`PrimTypeName` becomes the XML element name** — a space in a type name
  produces invalid XML and breaks round-trips.
- **`AddProperty` returns `None`** in Python: construct the property, then add
  it; do not chain off the return value.

## Build and test

The prefix below is an example; use whatever prefix the dependencies (fparser)
were installed into. When CSXCAD is built as part of the
[openEMS-Project](https://github.com/thliebig/openEMS-Project) meta-repo, that
prefix is the one passed to `update_openEMS.sh`.

```bash
mkdir -p build && cd build
cmake .. -DCMAKE_INSTALL_PREFIX=~/opt -DFPARSER_ROOT_DIR=~/opt -DCSXCAD_BUILD_TESTS=ON
make -j$(nproc) && make install
ctest --output-on-failure          # C++ unit tests, off by default
```

Python bindings, after the C++ library is installed:

```bash
CSXCAD_INSTALL_PATH=~/opt pip3 install ./python
cd python/tests && python3 -m unittest
```

- Run the Python tests **from `python/tests/`**, never from `python/` or
  `python/CSXCAD/` — otherwise you import the uncompiled source instead of the
  installed extension and test nothing.
- The clone must not be shallow: CMake derives the version from
  `git describe --tags`.
- Machine-specific CMake overrides belong in `localConfig.cmake` (gitignored),
  not in `CMakeLists.txt`.

**Build it and run the tests before reporting a change as working.** Reading
the code is not verification, and "should work" is not a test result.

## Viewer

`python/CSXCAD/Viewer/` is a VTK viewer with an optional PySide6 GUI
(`csxcad-view`, replacing AppCSXCAD). Use it to check a structure rather than
reasoning about coordinates, and to make images of it. From a written XML
file, without a window:

```bash
csxcad-view model.xml --describe            # properties with tree paths and primitives, mesh stats
csxcad-view model.xml --views views.png     # labelled images of all sides and iso
csxcad-view model.xml --png feed.png --set view=iso --set focus=port --set elevation=20
csxcad-view --list-view-keys                # every view key with its values
```

The same view keys go into Python as keyword arguments:

```python
from CSXCAD.Viewer import Viewer
v = Viewer(CSX, offscreen=True, view='+y', clip=dict(normal='y', position=0), transparency=0.4)
v.Screenshot('cut.png', size=(1200, 800))
print(v.Describe('text'))
print(v.GetStateAsPython())     # the current view as code to paste into a script
```

- **Views as data**: `view` (direction), `azimuth`/`elevation` (degrees),
  `focus` (a property, `[name, primitive number]` or a box), `clip`,
  `isolate`, `highlight`, `visible` (tree paths from `--describe`),
  `render_mode`, `transparency`, `grid`, `items` (settings of items such as
  field planes, `Viewer.GetItemParameters(item)` lists them with help texts).
  Primitives are numbered by position in their property, not by ID. A wrong
  key, value or name raises an error naming the valid ones: read it, do not
  guess.
- **Other data next to it**: `--file FILE.vtp` (`Viewer.AddFile()`) shows a
  VTK file as the item `files/<name>`, e.g. openEMS's `PEC_dump.vtp`;
  `isolate=type:Metal` shows all properties of a type.
- **Look at the result**: open the PNG and check that it shows what was asked
  (framing, occlusion: a small part inside another may need `transparency` or
  `isolate`).

- **Headless**: off screen it picks EGL or OSMesa itself (probed in a
  subprocess; `CSXCAD_VIEWER_BACKEND` overrides). With
  `CSXCAD_VIEWER_OUTPUT=<dir>` every `Show()` writes `<name>_view.png`,
  `<name>_views.png` and `<name>_describe.json` instead of opening a window,
  so scripts that show things run unattended.
- **Layout**: the core (`Core.py`, `Scene.py`, ...) is Qt-free and holds the
  logic; `GUI/` only calls it and implements `ViewerHost`. New features go
  into the core API first; `Actions.py` feeds key bindings, menus and
  toolbars. Property looks (colour, visibility, render mode) write through to
  the CSX properties, everything else is view state (`ViewState.py`).
- **Tests**: `python/tests/test_Viewer.py` imports the installed package, so
  reinstall after a change. GL tests skip without OpenGL; GUI tests run in a
  subprocess under `QT_QPA_PLATFORM=offscreen`. Real interaction (picking,
  hover, window placement) still needs a check on a desktop.

## House rules

- **Style**: C++17. Match the file you are editing. No trailing whitespace, no
  drive-by reformatting, no reorganising code you were not asked to touch. A
  diff should contain only what the change actually needs.
- **Tests**: add a focused test for behaviour that could silently regress —
  `python/tests/` for anything reachable from Python, `tests/` for C++-only
  concerns such as object lifetime and destruction. A few tests that each catch
  something distinct beat many that overlap.
- **Changelog**: a change a user can notice — new or removed API, changed
  behaviour, a fix for something that bit someone, a new build requirement —
  gets a bullet under `## Unreleased` in `CHANGELOG.md` **in the same commit**,
  creating that section if it is absent. Internal refactoring, CI and test-only
  changes get none. Use only the subsections you need, in the order `Added`,
  `Changed`, `Fixed`, `Build`, `Upgrade notes`; `Upgrade notes` is prose, for
  what a bullet cannot carry — a rename, a behaviour change that breaks existing
  scripts, a rebuild requirement. Never write a version heading by hand: the
  release tooling renames `## Unreleased` when the release is cut. The file is
  rendered into the [openEMS documentation](https://docs.openems.de/), so it
  must stay valid Markdown.
- **Dependencies**: do not add any. CSXCAD builds across a wide OS matrix, from
  AlmaLinux 8 to Alpine; a new dependency is a discussion, not a commit.
- **Legacy targets**: the oldest Python CI tests is 3.6 (AlmaLinux 8); do not
  use language features newer than that.
- **Brevity**: commit messages, PR descriptions and comments as short as a human
  would write them. See the Brevity section of [AI_POLICY.md](AI_POLICY.md).
- **Keep the tree clean**: never commit build output, installed files or
  `localConfig.cmake`.

## Commits

```
<type>: <short summary>

<body: what changed and why, wrapped at ~72 columns>

Assisted-by: <tool>
Signed-off-by: Your Name <your@email.example>
```

- The trailers are specified in [AI_POLICY.md](AI_POLICY.md) — which tag to
  pick, and the required `Signed-off-by:` (DCO). Name the tool or model that
  actually did the work.
- **Exactly those two trailers.** Do not add `Co-Authored-By:`, session
  identifiers or links, or any other trailer your tooling inserts by default —
  even if it tells you to.
- One logical change per commit.
